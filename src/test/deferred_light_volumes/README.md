# 球体光照体积：真正按光源覆盖范围进行延迟着色

基于 `src/5.advanced_lighting/8.2.deferred_shading_volumes/` 的九个背包场景、
G-buffer、Blinn–Phong 光照及半径公式，新增独立 OpenGL 3.3 / C++17 示范。
默认 128 盏灯，可切换 32 / 512 盏灯。增加地板便于观察光照分布。

## 先理解球体的作用

球体不是场景中新增加的发光实体，而是“本盏灯需要计算哪些屏幕像素”的代理。
光栅化球体时，片元着色器读取该屏幕像素的 **G-buffer 场景表面**，计算表面的受光。
球体投影之外不会启动这盏灯的片元着色器；投影之内仍可能有球外的场景表面，
所以还要根据 G-buffer 世界位置进行半径判断。球体投影是候选范围，并非精确的受光像素集合。

流程：

1. **几何阶段**：背包和地板各画一次，写入位置、法线、颜色/高光及深度。
2. **环境光阶段**：全屏画一次 `albedo * 0.1`。背景由位置附件的 alpha 区分。
3. **逐灯阶段**：CPU 遍历光源，设置一个光源的 uniforms，画以光源为中心、半径为规模的球体。
   `light.fs` 没有光源数组或光源循环，只算这一盏灯的漫反射、高光与衰减。
4. **加法混合**：`GL_FUNC_ADD` + `GL_ONE, GL_ONE`，将每盏灯的贡献加到已有颜色上。
5. **展示阶段**：在浮点 HDR 附件中完成累积后，统一进行曝光、色调映射和 gamma 处理。

## 为什么只画背面？为什么关闭深度测试？

- 一个闭合球有前后两层。如果不剔除，往往同一像素会把同一盏灯累加两次。
- 球的三角形从外部看为 CCW。开启 `GL_CULL_FACE`，设置 `glCullFace(GL_FRONT)`，
  留下背面。相机进入球体后，能看到的内表面正是背面，因此灯不会突然消失。
- 背面通常位于场景表面之后，直接用 `GL_LESS` 会拒绝有效光照。本示范在光照阶段
  关闭深度测试、关闭深度写入，使用 G-buffer 的位置与半径判定。灯泡和线框阶段才恢复深度测试。
- G-buffer 与光照 FBO 共享一个深度附件，用于灯泡被场景遮挡；没有深度附件采样反馈。
  光照阶段只改颜色，不清除或写入场景深度。

## 两个容易遗漏的边界情况

- 三角形球面是数学球的内接近似，直接缩放可能漏掉球边缘。`Sphere` 根据最小面平面距离
  算出保守外扩比例，确保光栅化代理包住数学球；光照半径仍使用原始半径。
  `V` 显示的是原始数学半径的线框近似。
- 背面被远裁剪面截掉时会漏光。CPU 检查球体是否可能触及远平面，保守退回该灯的全屏绘制。
  这仍是单灯着色器，窗口标题显示退回数量。正常视点下相机进入球体无需退回。

## 预期现象与操作

| 操作 | 作用 |
| --- | --- |
| `F1` / `F2` | 球体体积 / 逐灯全屏对照；同一视点、灯数、曝光下受光应一致 |
| `1` / `2` / `3` | 32 / 128 / 512 盏灯，使用同一固定随机序列的前 N 盏灯 |
| `V` | 显示前八盏灯的体积线框；灯泡小立方体表示实际光源位置 |
| `C` | 将相机放在第一盏橙色灯的中心，观察进入体积后仍有受光 |
| `R` | 恢复初始相机 |
| `WASD`、鼠标、滚轮 | 移动、转向、缩放视角 |
| `Q` / `E` | 降低 / 提高曝光，观察大量灯重叠后的亮度 |
| `Tab` / `Esc` | 释放或捕获鼠标 / 退出 |

窗口标题显示灯数、光照阶段的 GPU 毫秒数、相机所在体积数、远平面退回数量和曝光。
计时只覆盖环境光与逐灯累积，不包括几何、灯泡、线框、最终显示；异步读取最近完成的查询，
切换模式后等一会儿再比较。关闭垂直同步，线框也建议关闭后再比较性能。

`F2` 是**逐灯全屏绘制**：复用完全相同的单灯片元着色器，仍然进行加法混合，
用来隔离“光栅化覆盖范围”这个变量。它不是原章节“一次全屏 draw 中循环所有灯”的性能基线。
两种方式有相同的光源数量与 draw 次数，但体积模式通常少启动很多候选片元。

## 性能说法的准确含义

GPU 分支并非总是执行全部分支，也不是完全没有用；同组线程走不同路径时可能降低效率，
具体行为依赖硬件和编译器。这里的收益来自从光栅化阶段缩小候选范围。

延迟着色将物体几何处理与光源处理拆开，但总光照成本并非严格的“物体数 + 光源数”。
更接近“几何阶段成本 + 所有光源投影覆盖像素数之和 + 逐灯绘制开销”。
大量灯体积重叠、相机处于大球中、球占满屏幕时，收益会减小；球体顶点、draw call、混合写入也有成本。
此示范强调算法正确性，未加入 stencil、instancing、tiled/clustered lighting 或 MSAA。
因此不要预期所有视点和显卡下体积模式一定更快。

半径沿用 8.2 的 `5/256` 衰减阈值，边界之外直接截断，两种模式使用同样的近似。
最后统一色调映射使大量光源的累积不在 8-bit 附件中提前饱和；画面亮度不会与原章节逐值相同。

## 构建与运行

在仓库根目录执行 PowerShell：

```powershell
cmake -S . -B build -A x64
cmake --build build --config Debug --target test__deferred_light_volumes
Push-Location .\bin\test\Debug
.\test__deferred_light_volumes.exe
Pop-Location
```

资源随构建复制到可执行文件旁的 `deferred_light_volumes/`，共享模型由 `FileSystem::getPath` 定位。
示范在窗口尺寸变化时重建所有附件；最小化时暂停绘制。Release 对应 `bin/test/Release/`。

实际 GPU 对照验证（创建隐藏窗口，结束后自动退出）：

```powershell
Push-Location .\bin\test\Debug
.\test__deferred_light_volumes.exe --verify
Pop-Location
```

验证着色器链接、FBO 完整性、有实际光照的非空画面，以及 32/128/512 灯、球内相机、
贴近体积边界、远平面裁剪和尺寸重建时，两种模式的 HDR 像素是否一致（通道容差 0.002）。
最后也绘制灯泡、线框和展示阶段并检查 OpenGL 错误。失败返回非零退出码。

本次验证记录：Debug 目标构建成功；在 Intel(R) Arc(TM) Graphics 上实际运行 `--verify`，
上述 9 组对照全部通过，最大 HDR 通道误差均为 0，未发现 OpenGL 错误。
这是隐藏窗口的 GPU 渲染验证；尚未进行人工交互操作检查。

## 阅读代码

- `main.cpp`：`radiusFor`、`Sphere`、`geometryPass`、`lightingPass` 是主要学习入口。
- `assets/light.fs`：用屏幕像素读取 G-buffer，只输出一盏灯的贡献。
- `assets/volume.vs`：只负责把代理球变换到屏幕上，不输出球面的材质属性。
- `geometry.h`、几何与灯泡顶点着色器复用 8.2；关键改动带有中文注释。
